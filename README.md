## Featured project

### NexoEdu — Riwi × Mayor's Office of Barranquilla

Web platform for tracking and updating student and graduate records across public schools in the District of Barranquilla. Capstone project at Riwi in partnership with the city government, **currently live in production**.

**The problem.** Records lived scattered across spreadsheets and ad-hoc forms. They went stale quickly, and there was no way to tell when each record was last updated — leaving the city unable to track outcomes or run programs on reliable data.

**The solution.** An update campaign system. Each campaign defines a scope (district-wide, by locality, neighborhood or school) and eligibility criteria; the system automatically resolves which students qualify and records who updated their data and when. A data-freshness indicator and progress metrics turn "is our data current?" into something measurable.

**My role.**

- **Data modeling:** designed entities, attributes and relationships on a normalized relational schema, translating business rules into explicit database constraints — one administrator per school, exactly one scope type per campaign, a single update per student per campaign.
- **Front-end:** a vanilla JavaScript SPA, no framework. Custom History API router, session- and role-based route guards, a service layer over the REST API, a centralized HTTP client with automatic token refresh, and a reusable component system with skeleton screens and parallel data fetching.

**Stack:** JavaScript (ES Modules) · Vite · Tailwind CSS v4 · Node.js · Express · PostgreSQL · Supabase · JWT · bcrypt · Swagger
**Deployment:** front-end on Vercel · back-end on Render · database on Supabase

Built by a 6-person team using agile methodology.

## How I work

I'm still learning, so I won't sell principles I haven't tested. These I have:

- **Business rules belong where they can't be broken.** A rule that lives only in application code will eventually be bypassed by some path someone writes later. On NexoEdu we pushed the ones we could down into database constraints.
- **Understand before abstracting.** I wrote the router and the HTTP client by hand not out of purism, but because I wanted to know what a framework actually solves before depending on one.
- **Anticipate what will break.** I'd rather think through the edge case up front than patch it in production later.
